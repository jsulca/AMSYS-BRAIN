# MNT-043

## Título
Localizar los errores de validación en el campo que los provoca

## Tipo
UX

## Prioridad
MEDIUM

## Problema
Los errores de validación se muestran agrupados en un bloque, lejos del campo que los origina. En un
formulario con decenas de filas, un mensaje como *"La tarea nro. 17, es necesario que la duración sea
mayor a cero"* obliga al usuario a contar filas a mano.

## Objetivo
Que el usuario llegue al campo erróneo de un vistazo.

## Comportamiento actual
- El servidor responde `400` con `PartialView("_Error")`, una lista HTML de mensajes.
- El JavaScript la inyecta en `<div id="mensajes">` con `helper.error.show('#mensajes', responseText)`.
- Las claves de `ModelState` son genéricas por colección
  (`"Tareas_Duracion"`, `"Materiales_Cantidad"`), no por fila: no permiten identificar el elemento.
- El número de fila va **dentro del texto** del mensaje.
- No hay validación en cliente: cualquier error exige una ida y vuelta al servidor.
- No se hace desplazamiento hacia el error ni se resalta ninguna fila.

## Comportamiento esperado
- El campo o la fila con error se resalta.
- La vista se desplaza al primer error.
- Cuando el error está en una pestaña oculta, esa pestaña se marca y se activa.
- Las validaciones evidentes (obligatorio, mayor que cero) se comprueban en cliente antes de enviar.

## Reglas de negocio involucradas
Ninguna cambia. Las validaciones son las de `BR-TA-003`, `BR-PM-009`, `BR-AS-004`, `BR-AS-005`.

## Archivos potencialmente afectados
- Los controladores del área `Gestion` (claves de `ModelState` y formato de respuesta)
- `AMSYS.WebAdmin/Views/Shared/_Error.cshtml`
- `AMSYS.WebAdmin/wwwroot/js/` (`helper.error`)
- Las vistas de `Seccion`, `PlanMantenimiento` y `OrdenTrabajo`

## Entidades involucradas
Ninguna.

## Riesgos
- **MEDIO**: cambiar el formato de la respuesta de error afecta a **todas** las pantallas que usan
  `helper.error.show`, incluidas las de otros módulos. Hay que mantener compatibilidad o migrar todo.
- Duplicar las validaciones en cliente crea el riesgo de que diverjan de las del servidor. La
  validación de cliente es una **conveniencia**; el servidor sigue siendo la autoridad.

## Propuesta de solución
1. Cambiar las claves de `ModelState` a un formato indexado (`Tareas[16].Duracion`), sin alterar el
   texto del mensaje.
2. Añadir un modo de respuesta JSON estructurado (`{ campo: [mensajes] }`) manteniendo el
   `PartialView("_Error")` actual para las pantallas no migradas.
3. Ampliar `helper.error` para, cuando reciba JSON: resaltar el campo, activar la pestaña que lo
   contiene y desplazar la vista al primero.
4. Migrar pantalla por pantalla, empezando por `Seccion/Editar`, que es la de peor experiencia.
5. Añadir validación en cliente sólo para las comprobaciones triviales, marcando el campo al salir de
   él.

## Tests requeridos
- Error en la tarea 17 de 30: la fila se resalta y la vista se desplaza a ella.
- Error en una pestaña no activa: la pestaña se marca y se activa.
- Varios errores: se listan todos y se salta al primero.
- Las pantallas no migradas siguen mostrando los errores como hoy.
- Los textos de los mensajes no cambian.

## Criterios de aceptación
- [ ] El primer error recibe el foco y se resalta.
- [ ] Los errores en pestañas ocultas son alcanzables.
- [ ] Las pantallas no migradas no se rompen.
- [ ] El servidor sigue siendo la autoridad de validación.

## Fuera de alcance
- Migrar a FluentValidation (`MNT-025`).
- Otros módulos.

## Dependencias
Se coordina con `MNT-025` (unificación de validaciones) y `MNT-031` (extracción de JavaScript).

## Notas para Claude Code
- Mantén la compatibilidad con `helper.error.show`: lo usan pantallas de todo el sistema, no sólo de
  Mantenimiento. Detecta el tipo de respuesta en lugar de sustituir el mecanismo.
- **No sustituyas la validación de servidor por la de cliente.** Añádela como conveniencia.
