# MNT-005

## Título
Permitir desbloquear una asignación de plan (`Bloqueado`) atascada

## Tipo
BUSINESS_RULE

## Prioridad
CRITICAL

## Problema
Una asignación de plan con `TipoProgramacion = FLOTANTE` se marca `Bloqueado = true` al generar una
orden de trabajo, y sólo se desbloquea cuando esa orden alcanza un estado de cierre. **No existe
ninguna acción de interfaz que permita desbloquearla manualmente.** Si el desbloqueo automático no
ocurre, el equipo o la ubicación deja de recibir mantenimiento preventivo **de forma permanente y
sin remedio disponible para el usuario**.

## Objetivo
Que un usuario autorizado pueda diagnosticar y desbloquear una asignación atascada, con trazabilidad.

## Comportamiento actual
- Bloqueo: `PlanMantenimiento.Logica.cs:217`, `:283`, `:370` →
  `equipo.Bloqueado = equipo.TipoProgramacion == TipoProgramacion.FLOTANTE;`
- Exclusión: `PlanMantenimiento.Logica.cs:161` y `:312` →
  `GetAllByQueryable(x => !x.Bloqueado && ...)`.
- Desbloqueo: sólo en `OrdenTrabajo.Logica.cs:420-443` (`ActualizarAsync`), `:684-745`
  (`NotificarAsync`) y `:829-875` (`ActualizarEstadoAsync`), condicionado a `!existeCierre`.
- UI: `PlanMantenimiento/Ver.cshtml:199` y `:255` sólo **muestran** `SI`/`NO` en rojo.
- `PlanMantenimientoEquipoLogica.ActualizarAsync` **no** toca `Bloqueado`, por lo que editar la
  asignación tampoco lo libera.

### Escenarios verificados que dejan la asignación muerta
1. La OT que causó el bloqueo se elimina de base de datos.
2. La OT se creó ya en un estado de cierre (`BR-OT-006` siembra logs de cierre) → cuando después se
   intenta el desbloqueo, `existeCierre` ya es `true` y el bloque se omite.
3. Bug de variable en `OrdenTrabajo.Logica.cs:225`: la condición usa `_.Estado == ANULADO` en lugar
   de `x.Estado == ANULADO`, por lo que para una OT ya anulada `existeCierre` da `true` con
   cualquier log y el desbloqueo nunca se ejecuta (ver `MNT-011`).

## Comportamiento esperado
- La pantalla `PlanMantenimiento/Ver` muestra, para cada asignación bloqueada, **qué OT la bloquea**
  (o indica que no se encontró ninguna abierta) con enlace directo.
- Existe una acción *Desbloquear* con confirmación explícita, protegida por permiso.
- El desbloqueo queda registrado (quién, cuándo, por qué).
- Desbloquear **no** altera `PosicionActual`, `ContadorActual` ni `UltimaEjecucion`.

## Riesgos
- **ALTO**: desbloquear una asignación cuya OT sigue realmente abierta genera una **segunda OT**
  para el mismo ciclo. Por eso la acción debe mostrar la OT bloqueante y exigir confirmación.
- Sin el permiso adecuado, cualquier usuario podría forzar generación duplicada (`MNT-001` es
  prerrequisito).
- El nuevo endpoint hereda el IDOR de `MNT-028` si no se filtra por `EmpresaId`.

## Propuesta de solución
1. **Diagnóstico primero** (esta parte es de bajo riesgo y aporta valor inmediato):
   en `PlanMantenimiento/Ver`, para cada asignación con `Bloqueado = true`, mostrar la última OT de
   `(PlanMantenimientoId, EquipoId|UbicacionId)` con su código y estado.
2. Añadir `DesbloquearAsync(int id, int empresaId, int usuarioId)` en ambas lógicas, filtrando
   **siempre** por `EmpresaId`.
3. Nuevas acciones POST `Desbloquear` con `[FiltroAccion]`.
4. Confirmación en la UI mostrando la OT bloqueante y advirtiendo del riesgo de duplicación.
5. Registrar la acción (mínimo: un `OrdenTrabajoLog` no aplica aquí; considerar una tabla de
   auditoría o, temporalmente, un `ILogger` — coordinar con `MNT-020`).

## Tests requeridos
- Asignación FLOTANTE bloqueada + OT cerrada → desbloquear la deja generando de nuevo.
- Asignación bloqueada + OT abierta → la UI advierte y, si se confirma, se desbloquea.
- Desbloquear no altera `PosicionActual`, `ContadorActual` ni `UltimaEjecucion`.
- Un usuario de otra empresa recibe `400`/`401`, no desbloquea nada.
- Una asignación FIJA no muestra la acción (nunca está bloqueada).

## Criterios de aceptación
- [ ] `PlanMantenimiento/Ver` muestra la OT bloqueante de cada asignación bloqueada.
- [ ] Existe una acción de desbloqueo protegida por permiso y filtrada por empresa.
- [ ] El desbloqueo no modifica el avance del ciclo.
- [ ] La confirmación advierte del riesgo de generar una OT duplicada.

  y debería ejecutarse antes o en paralelo.
- Rediseñar el mecanismo de bloqueo.

## Dependencias

## Notas para Claude Code
- **No elimines el mecanismo de bloqueo.** Es una regla de negocio válida (`BR-GE-008`): impide que
  un plan flotante avance mientras el trabajo anterior no se ha ejecutado.
- El desbloqueo manual y el automático deben usar el **mismo** método de la capa lógica.
- No confundas esta tarea con `MNT-006`: aquí se libera el bloqueo, allí se evita el reinicio
  accidental del ciclo.
