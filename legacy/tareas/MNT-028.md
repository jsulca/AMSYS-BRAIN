# MNT-028

## Título
Cerrar el IDOR entre empresas en la edición de asignaciones de Plan

## Tipo
SECURITY

## Prioridad
CRITICAL

## Problema
Las acciones POST de edición de `PlanMantenimientoEquipo` y `PlanMantenimientoUbicacion` resuelven el
registro por su identificador **sin filtrar por empresa**, en el controlador y también en la capa
lógica. Un usuario de la empresa A puede modificar la programación de mantenimiento de un equipo de
la empresa B iterando identificadores. Además, por `BR-AS-007`, esa edición **reinicia el ciclo de
mantenimiento** de la víctima.

## Objetivo
Que ninguna escritura del módulo pueda alcanzar datos de otra empresa.

## Comportamiento actual

`PlanMantenimientoEquipo.Controller.cs` (`Editar` POST):
```csharp
public async Task<IActionResult> Editar(PlanMantenimientoEquipoModel.Editar model)
{
    // no recibe UserInformation
    PlanMantenimientoEquipo entidad = (await _planMantenimientoEquipoServicio.BuscarPorIdAsync(model.Id!.Value))!;
    ...
    await _planMantenimientoEquipoServicio.ActualizarAsync(_);
}
```
`PlanMantenimientoEquipo.Logica.cs`:
```csharp
public Task ActualizarAsync(PlanMantenimientoEquipo entidad)
{
    PlanMantenimientoEquipo? _ = _repositorio.GetOne(x => x!.Id == entidad.Id);   // sin EmpresaId
```
`PlanMantenimientoUbicacion` presenta exactamente el mismo defecto.

Contraste: las acciones `Eliminar` y `Editar` (GET) **sí** comprueban la empresa mediante
`ContarAsync(new { Id, EmpresaId })`. La omisión en el POST es un descuido.

Impacto combinado:
1. Reinicio del ciclo de mantenimiento de un equipo ajeno (pérdida de posición, contador y última
   ejecución).
2. Cambio de `TipoProgramacion` ajeno.
3. `BuscarPorIdAsync` incluye `PlanMantenimiento` y `Equipo`: la respuesta de error podría revelar
   datos ajenos.

Agravante: ninguna de estas acciones tiene `[FiltroAccion]` (`MNT-001`), así que el atacante sólo
necesita una sesión válida cualquiera.

## Comportamiento esperado
- El controlador recibe `UserInformation` y pasa `EmpresaId`.
- La capa lógica filtra por `EmpresaId` **también** (defensa en profundidad).
- Un identificador ajeno devuelve "no encontrado", indistinguible de uno inexistente.

## Riesgos
- **BAJO**: el cambio sólo restringe. Ningún uso legítimo depende de editar registros de otra empresa.
- Cambiar la firma de `BuscarPorIdAsync` y `ActualizarAsync` afecta a sus llamadores: localizarlos
  todos antes.
- La filtración por empresa se hace vía `PlanMantenimiento.EmpresaId` (así lo hace ya
  `PlanMantenimientoEquipoFiltro.EmpresaId`); reutiliza ese mecanismo.

## Propuesta de solución
1. Añadir `UserInformation usuario` a ambas acciones `Editar` POST.
2. Cambiar `BuscarPorIdAsync(int id)` por `BuscarPorIdAsync(int id, int empresaId)` — o por filtro,
   siguiendo el patrón dominante del módulo.
3. Añadir el filtro de empresa en `ActualizarAsync` y en `EliminarAsync` de ambas lógicas
   (defensa en profundidad, aunque el controlador ya valide).
4. Si no se encuentra el registro, devolver `400` con el mismo mensaje genérico que hoy.
5. **Auditar** el resto del módulo buscando `GetOne(x => x.Id == ...)` sin `EmpresaId`.

## Tests requeridos
- Usuario de A edita una asignación de A → funciona.
- Usuario de A edita una asignación de B → `400`; el registro de B **no cambia**.
- Verificar explícitamente que `PosicionActual` y `UltimaEjecucion` de la víctima no se modificaron.
- Eliminar sigue funcionando dentro de la propia empresa.
- Ningún dato de la otra empresa aparece en la respuesta de error.

## Criterios de aceptación
- [ ] Ambos POST `Editar` reciben y aplican `EmpresaId`.
- [ ] La capa lógica filtra por empresa de forma independiente.
- [ ] Prueba de intento cruzado documentada, con verificación de no modificación.
- [ ] Auditoría del patrón en el resto del módulo documentada.

## Notas para Claude Code
- Filtra **en la capa lógica**, no sólo en el controlador. Los servicios se consumen también desde
  la API móvil y desde otros controladores; la validación en un único punto es frágil.
- El filtro se aplica sobre `PlanMantenimiento.EmpresaId`, no sobre la asignación: ésta no tiene
  `EmpresaId` propio.
