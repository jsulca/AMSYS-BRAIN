# MNT-032

## Título
Corregir la selección y la retroalimentación de la generación de órdenes

## Tipo
UX

## Prioridad
HIGH

## Problema
La acción que crea órdenes de trabajo reales — irreversible — tiene la peor retroalimentación del
módulo: la selección puede quedar vacía sin que el usuario lo sepa, y un fallo del servidor no
produce ningún mensaje.

## Objetivo
Que la acción más crítica del flujo sea también la que mejor comunica lo que va a hacer y lo que hizo.

## Comportamiento actual
`AMSYS.WebAdmin/Areas/Gestion/Views/OrdenTrabajo/Previsualizar.cshtml`:
```javascript
ObtenerModelo: () => {
    var checks = $('input[name="Rutina"]:checked:visible')   // :visible
    ...
}
$('#btnGenerar').click(function () {
    if (confirm('¿Esta seguro de generar las ordenes de trabajo ...?')) {
        $('#btnGenerar').attr('disabled', 'disabled')
        $.post('/Gestion/OrdenTrabajo/Previsualizar', model, ({ cantidad }) => {
            alert(`Se generaron ${cantidad} orden(es) de trabajo`)
            location.href = '/Gestion/OrdenTrabajo/Index'
        })                                                   // sin manejador de error
    }
})
```
Defectos:
1. **`:visible`**: los checkboxes viven en la pestaña *Tabla*. Si el usuario está en la pestaña
   *Tarjetas*, la selección se lee vacía → se envía un modelo sin elementos → el sistema responde
   *"Se generaron 0 orden(es) de trabajo"* sin explicar por qué.
2. **Sin manejador `error`**: ante un fallo del servidor no aparece nada; el botón queda deshabilitado
   de forma permanente y el usuario no sabe si se generó algo.
3. **`confirm()` / `alert()` nativos**, mientras el resto del módulo usa SweetAlert.
4. **`name="Rutina"`** como nombre del checkbox de selección: no tiene relación con lo que hace y
   confunde al leer el código.
5. No hay contador de selección: el usuario no sabe cuántas órdenes va a generar hasta después.
6. El botón no se deshabilita cuando la selección está vacía.

## Comportamiento esperado
- La selección se lee independientemente de la pestaña activa.
- Un contador visible indica "N de M órdenes seleccionadas".
- El botón está deshabilitado si N = 0.
- La confirmación indica el número exacto de órdenes que se crearán.
- El resultado y los errores se comunican con el mismo estilo que el resto del módulo.
- Ante un error, el botón se vuelve a habilitar.

## Riesgos
- **BAJO-MEDIO**: hay que comprobar cómo se comporta el POST cuando `entidades` llega vacío o nulo.
  `OrdenTrabajoModel.Previsualizar[] entidades` sin parámetros podría enlazarse a `null` y provocar
  `NullReferenceException` en `entidades.Select(...)`. **Verificar y blindar el controlador.**
- Cambiar el selector `:visible` altera qué se envía: hay que asegurarse de que la vista de tarjetas
  y la de tabla tengan checkboxes sincronizados, o unificarlos.

## Propuesta de solución
1. Blindar el controlador contra `entidades` nulo o vacío: devolver un mensaje explícito, no un `500`
   ni un silencioso `0`.
2. Quitar `:visible` del selector; sincronizar la selección entre ambas pestañas o dejar los
   checkboxes sólo en una y reflejarlos en la otra.
3. Renombrar el checkbox (`name="ordenSeleccionada"`) y actualizar el selector correspondiente.
4. Añadir un contador de selección junto al botón, actualizado en cada cambio.
5. Deshabilitar el botón cuando la selección esté vacía.
6. Sustituir `confirm`/`alert` por `Swal.fire`, incluyendo el número de órdenes en el texto.
7. Añadir manejadores `error` y `complete` al `$.post`, rehabilitando el botón.

## Tests requeridos
- Seleccionar 3 órdenes en la pestaña Tabla y generar → se crean 3.
- Cambiar a la pestaña Tarjetas con 3 seleccionadas y generar → se crean **3** (hoy 0).
- Sin selección → el botón está deshabilitado.
- Provocar un error del servidor → mensaje visible y botón rehabilitado.
- POST manipulado sin `entidades` → mensaje claro, no `500`.
