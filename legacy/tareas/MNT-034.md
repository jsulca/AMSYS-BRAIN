# MNT-034

## Título
Resolver los permisos a nivel de Elemento (código muerto)

## Tipo
SECURITY

## Prioridad
MEDIUM

## Problema
El sistema tiene un segundo nivel de permisos —por `Elemento` dentro de una `Pagina`, pensado para
mostrar u ocultar botones según el rol— que se configura, se persiste, se carga en la sesión y se
calcula en cada petición, pero **ninguna vista lo consume**. Además, el cálculo parece incorrecto.

## Objetivo
Que el permiso a nivel de elemento funcione o desaparezca; no que dé la impresión de funcionar.

## Comportamiento actual
`AMSYS.WebAdmin/Commons/Session/FiltroAccion.cs`:
```csharp
var page = user.Paginas?.FirstOrDefault(x => url!.ToLower() == $"/{x.Area}/{x.Controlador}/{x.Accion}".ToLower());
if (page != null)
{
    var controller = filterContext.Controller as Controller;
    controller!.ViewBag.Elements = user.Elementos.Where(x => x.Id == page.Id).ToList();
}
```
- Búsqueda de `ViewBag.Elements` en todas las vistas `.cshtml`: **0 resultados**.
- El filtro compara `Elemento.Id` con `Pagina.Id`. Según el modelo
  (`AMSYS.Entidades/Seguridad/Genericos/Elemento.cs`), `Elemento` tiene `Id` **y** `PaginaId`; la
  comparación correcta sería `x.PaginaId == page.Id`. `INFERENCIA` — no se puede confirmar sin ver
  los datos reales de la tabla `elemento`.
- La UI de administración de roles sí permite configurar elementos por rol.

Resultado: el administrador cree que puede ocultar botones por rol; no puede.

## Comportamiento esperado
**DECISIÓN PENDIENTE** (`D-14`), análoga a `MNT-002`:
- **Opción A — Implementar**: corregir la comparación y consumir `ViewBag.Elements` en las vistas del
  módulo para mostrar u ocultar acciones. Es un trabajo amplio: hay que dar de alta un `Elemento` por
  cada botón y condicionar cada uno.
- **Opción B — Retirar**: eliminar la UI de configuración de elementos y documentar que el permiso
  más fino disponible es la página.

## Reglas de negocio involucradas
Ninguna de dominio. Ver `analysis/permissions.md` SEC-06.

## Archivos potencialmente afectados
- `AMSYS.WebAdmin/Commons/Session/FiltroAccion.cs`
- `AMSYS.WebAdmin/Areas/Seguridad/**` (UI de configuración)
- Todas las vistas del área `Gestion` (sólo en la Opción A)

## Entidades involucradas
`Elemento`, `RolElemento`, `Pagina`, `Rol`

## Riesgos
- **MEDIO en la Opción A**: al corregir la comparación, `ViewBag.Elements` empezaría a devolver
  contenido. Como ninguna vista lo usa, no habría efecto inmediato — pero cualquier vista que se
  añada después heredaría la semántica. Hay que definirla antes de corregir.
- Ocultar botones es una mejora de usabilidad, **no** un control de seguridad: el endpoint sigue
  siendo accesible. Sin `MNT-001`, ocultar el botón no protege nada.

## Propuesta de solución
1. Auditar los datos: cuántas filas hay en `elemento` y `rolelemento`, y si están asociadas a páginas
   del área `Gestion`.
2. Plantear `D-14` al propietario con esa información.
3. Si es la Opción A:
   - corregir la comparación a `x.PaginaId == page.Id` (verificando antes con datos reales),
   - implementar el consumo **sólo en una pantalla piloto** y evaluar,
   - documentar la convención antes de extenderla.
4. Si es la Opción B: retirar la UI, **sin borrar tablas ni datos**, y documentarlo.

## Tests requeridos
- Opción A: un rol sin cierto elemento no ve ese botón; el rol que lo tiene, sí. El endpoint sigue
  protegido por `MNT-001` independientemente.
- Opción B: la UI de roles ya no ofrece elementos y el resto de la configuración funciona igual.
- En ambos casos: iniciar sesión y navegar por el módulo no produce errores.
