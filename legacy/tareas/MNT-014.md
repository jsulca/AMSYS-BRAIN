# MNT-014

## Título
Corregir la actualización de Sección: identidad de tareas y adjuntos que no se pueden eliminar

## Tipo
DATA_INTEGRITY

## Prioridad
HIGH

## Problema
Al guardar una sección se **borran y recrean** todas sus tareas, materiales y servicios, cambiando
sus identificadores en cada guardado. Además, los adjuntos sólo se pueden añadir: no existe forma de
eliminarlos.

## Objetivo
Preservar la identidad de las tareas entre guardados y permitir gestionar los adjuntos por completo.

## Comportamiento actual
`AMSYS.Logicas/Gestion/Seccion.Logica.cs:26-79`:
```csharp
List<Tarea> tareas = tareaRepositorio.GetAllBy(x => x!.SeccionId == _.Id);
if (tareas.Count > 0) tareaRepositorio.Remove(tareas);
foreach (Tarea item in entidad.Tareas) { item.SeccionId = _.Id; tareaRepositorio.Save(item); }
```
Mismo patrón para `SeccionMaterial` y `SeccionServicio`. Para `Adjuntos` **sólo** hay `Save`.

Consecuencias verificadas:
1. Cambiar una coma en la descripción de una tarea reasigna los `Id` de las 30 tareas de la sección.
2. Sin `Id` estable no se puede construir historial, ni versionado, ni comparar plantilla vs.
   ejecución a nivel de tarea.
3. Los `Id` de la secuencia crecen sin control (cada guardado consume tantos como tareas haya).
4. Un adjunto subido por error queda en la sección para siempre.

**Aspecto tranquilizador verificado**: `OrdenTrabajoTarea` guarda un *snapshot* por valor y
referencia `SeccionId`, **no** `TareaId`. Por tanto el borrado no rompe las órdenes históricas.
Este hecho reduce el riesgo del cambio y debe conservarse.

## Comportamiento esperado
- Las tareas existentes se actualizan; las nuevas se insertan; las quitadas se eliminan. Los `Id` de
  las que permanecen no cambian.
- Los adjuntos se pueden eliminar desde la interfaz.

## Riesgos
- **ALTO**: el JavaScript de la vista **no envía hoy el `Id`** de cada tarea (construye
  `tareas[i].orden`, `tareas[i].descripcion`, …). Sin `Id` no se puede distinguir "editada" de
  "nueva". Hay que modificar la vista **y** el modelo, coordinadamente.
- Si el `Id` llega vacío o manipulado, se podrían actualizar tareas de otra sección: hay que validar
  que cada `Id` recibido pertenece a la sección que se edita.
- El patrón *delete-all* funciona hoy; sustituirlo introduce lógica de conciliación nueva, que es
  donde suelen aparecer bugs.

## Propuesta de solución
1. Añadir `Id` al binding de `Tarea[]`, `SeccionMaterial[]` y `SeccionServicio[]`, y emitirlo desde
   la vista como `data-id` + campo oculto.
2. En `ActualizarAsync`, conciliar por `Id`:
   - `Id == 0` → insertar
   - `Id > 0` y presente en el request → actualizar
   - presente en base de datos y ausente del request → eliminar
   - **validar** que todo `Id > 0` recibido pertenece a `_.Id`
3. Aplicar el mismo patrón a los adjuntos y añadir el botón de eliminar en la pestaña *Adjuntos*.
4. Envolver en transacción (coordinar con `MNT-013`).

## Tests requeridos
- Editar la descripción de una tarea: el `Id` de esa tarea y el de las demás no cambian.
- Añadir una tarea: se inserta; las existentes conservan su `Id`.
- Quitar una tarea: se elimina; las demás conservan su `Id`.
- Reordenar tareas: no se recrean.
- Enviar un `Id` de una tarea de otra sección → rechazado.
- Eliminar un adjunto: desaparece de la sección.
- Las OT generadas antes del cambio siguen mostrando correctamente su sección de origen.
