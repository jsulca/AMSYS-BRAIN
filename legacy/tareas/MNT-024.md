# MNT-024

## Título
Validar el campo `Orden` de las Tareas de una Sección

## Tipo
VALIDATION

## Prioridad
MEDIUM

## Problema
`Tarea.Orden` determina la secuencia de ejecución de las tareas dentro de una orden de trabajo, pero
no se valida en ningún punto. Admite cero, negativos y duplicados dentro de la misma sección, lo que
produce un orden de ejecución indeterminado.

## Objetivo
Que la secuencia de ejecución de las tareas sea siempre determinista y significativa.

## Comportamiento actual
- `Validar(SeccionModel.Nuevo/Editar)` valida `TipoTareaId`, `EspecialidadId`, `Descripcion`,
  `Cantidad` y `Duracion`. **No menciona `Orden`.**
- La vista asigna `value="${i}"` al crear filas nuevas por JavaScript, pero el campo es editable y se
  envía tal cual.
- `TareaRepositorio.Listar` ordena por `Orden`; ante empates, el orden lo decide PostgreSQL y no está
  garantizado entre ejecuciones.
- Al generar la OT (`BR-TA-004`) se aplica `.OrderBy(x => x.Orden)`.

Agravante documentado en `BR-TA-004`: cuando una posición del plan ejecuta **varias** secciones, las
tareas de todas ellas se mezclan y se ordenan sólo por `Orden`. Dos secciones distintas con tareas en
el orden 1, 2, 3 producen una secuencia intercalada (1,1,2,2,3,3) que probablemente no es la deseada.

## Comportamiento esperado
- `Orden` es un entero positivo.
- No se repite dentro de la misma sección.
- **DECISIÓN MENOR** (`D-10`): cuando una OT combina varias secciones, ¿deben agruparse las tareas
  por sección y ordenarse dentro de cada grupo, o mantenerse la mezcla actual?

`Tarea`, `Seccion`, `OrdenTrabajoTarea`

## Riesgos
- **MEDIO**: pueden existir secciones con `Orden` duplicado o cero en producción. Añadir la
  validación impediría **editar** esas secciones hasta corregirlas. Diagnosticar antes.
- Cambiar la agrupación de tareas en la OT (`D-10`) altera lo que ve el técnico: no hacerlo sin
  decisión expresa.

## Propuesta de solución
1. Diagnóstico: secciones con `Orden` duplicado, cero o negativo.
2. Validar `Orden > 0` y unicidad dentro de la sección, con mensajes por fila.
3. Mejorar la UI: renumerar automáticamente al añadir, eliminar o reordenar filas, y ofrecer
   arrastrar y soltar (o botones subir/bajar) en lugar de escribir el número a mano.
4. Si el diagnóstico revela muchos casos, ofrecer una renumeración asistida al abrir la sección.
5. Plantear `D-10` al propietario.

## Tests requeridos
- Guardar con `Orden` duplicado → `400` indicando las filas afectadas.
- Guardar con `Orden = 0` o negativo → `400`.
- Reordenar filas en la UI → los valores se renumeran solos y el guardado funciona.
- Secciones existentes con orden válido → sin cambios.
- La OT generada respeta el orden.

## Criterios de aceptación
- [ ] Diagnóstico entregado.
- [ ] `Orden` validado como positivo y único por sección.
- [ ] La UI renumera automáticamente.
- [ ] Decisión `D-10` registrada (implementarla puede ser una tarea aparte).

## Fuera de alcance
- Cambiar la agrupación de tareas en la OT sin decisión.
- Corregir datos existentes de forma masiva.

## Dependencias
Se coordina con `MNT-014`, que modifica el mismo binding y las mismas vistas. **Conviene ejecutarlas
juntas** para no tocar dos veces el mismo JavaScript.

## Notas para Claude Code
- La mejora de UI (renumeración automática) resuelve el problema de raíz mejor que la validación:
  si el usuario nunca escribe el número, nunca lo duplica. Prioriza esa parte.
- No renumeres automáticamente las secciones existentes al abrirlas: sería un cambio silencioso de
  datos. Ofrécelo como acción explícita.
