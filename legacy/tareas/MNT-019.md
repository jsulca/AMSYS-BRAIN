# MNT-019

## Título
Crear el proyecto de tests y cubrir el cálculo de posiciones del Plan de Mantenimiento

## Tipo
TESTING

## Prioridad
HIGH

## Problema
La solución **no tiene ningún proyecto de tests**. El algoritmo más crítico y menos evidente del
sistema — el cálculo de qué secciones se ejecutan en cada posición del plan — no tiene ninguna red
de seguridad. Toda tarea de este backlog que toque `PlanMantenimiento` o `OrdenTrabajo` es hoy un
cambio a ciegas.

## Objetivo
Establecer una base de tests mínima pero real, empezando por la lógica pura de dominio, para que las
demás tareas puedan ejecutarse con seguridad.

## Comportamiento actual
- `AMSYS.sln` contiene 10 proyectos, ninguno de tests.
- No hay CI, ni scripts de prueba, ni fixtures.
- La verificación es manual, por pantalla.

## Comportamiento esperado
- Existe `AMSYS.Tests` (xUnit) referenciando `AMSYS.Entidades`.
- `PlanMantenimiento.Adicional.cs` está cubierto al 100 % de ramas.
- El proyecto se ejecuta con `dotnet test` sin necesidad de base de datos.

## Reglas de negocio involucradas
Las que se convierten en tests (todas `CONFIRMED`):
`BR-PM-003`, `BR-PM-005`, `BR-PM-006`, `BR-PM-007`, `BR-OT-002`, `BR-AV-001`

## Archivos potencialmente afectados
- `AMSYS.sln`
- Nuevo proyecto `AMSYS.Tests`
- Ningún archivo de producción se modifica

## Entidades involucradas
`PlanMantenimiento`, `PlanMantenimientoSeccion`, `OrdenTrabajo`, `Aviso` (sólo lectura, en memoria)

## Riesgos
- **MUY BAJO**: no toca código de producción.
- Riesgo de sobre-ingeniería: no montar mocks de EF ni infraestructura pesada en esta primera tarea.

## Propuesta de solución
1. Crear `AMSYS.Tests` (xUnit) y añadirlo a la solución.
2. Cubrir `PlanMantenimiento.Adicional.cs`:
   - `Comportamiento()` con distintos `Intervalo` y `CantidadPosiciones`.
   - `ComportamientoConFactorPlanificacion()`.
   - `ComportamientoConSeccion()` y `ComportamientoConPlanMantenimientoSeccion()`:
     - sección única,
     - varias secciones con intervalos 1/2/4 (caso documentado en `analysis/orders.md` §5),
     - **empate de `Nivel`** (documenta el comportamiento actual: se conservan ambas — ver `BR-UNK-001`),
     - posición sin secciones aplicables,
     - `Secciones` nulo y `Secciones` vacío,
     - `CantidadPosiciones = 0`.
3. Cubrir `OrdenTrabajo.Adicional.cs`: `EstadosHabilitados()`, `PuedoEditar`, `PuedoNotificar`,
   `CalcularPorcentaje()` (incluido `TotalTareas = 0`).
4. Cubrir `Aviso.Adicional.cs`: `EstadosHabilitados()`, `ObtenerTiempoParada()` con fechas nulas.
5. Cubrir `NumeroUtilitario.MCM` / `MCD`, incluido el array vacío (relevante para `MNT-012`).

## Tests requeridos
Los descritos en la propuesta. **Los tests documentan el comportamiento actual, no el deseado**: si
un test revela un bug, se anota con un comentario y se crea la tarea correspondiente; **no se
corrige el código en esta tarea**.

## Criterios de aceptación
- [ ] `dotnet test` se ejecuta y pasa sin base de datos.
- [ ] `PlanMantenimiento.Adicional.cs` con cobertura de ramas completa.
- [ ] Cada test cita la regla `BR-XX-NNN` que verifica.
- [ ] Los comportamientos sorprendentes están anotados y enlazados a una tarea.

## Fuera de alcance
- Tests de integración con base de datos.
- Tests de controladores o de UI.
- CI/CD.
- **Corregir cualquier bug que los tests revelen.**

## Dependencias
Ninguna. **Debería ser la primera tarea técnica que se ejecute**, junto con `MNT-001`.

## Notas para Claude Code
- No cambies ni una línea de producción en esta tarea. Si un test falla porque el código tiene un
  bug, escribe el test contra el comportamiento **actual**, con un comentario
  `// TODO(MNT-XXX): comportamiento cuestionable` y crea o referencia la tarea.
- Empieza por `AMSYS.Entidades` porque no tiene dependencias de infraestructura: es la capa donde
  los tests aportan más valor con menos esfuerzo.
- Usa la versión de .NET del resto de la solución (revisa los `.csproj` antes de crear el proyecto).
