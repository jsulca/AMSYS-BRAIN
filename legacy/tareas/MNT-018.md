# MNT-018

## Título
Validar órdenes de trabajo pendientes antes de eliminar una asignación de plan

## Tipo
DATA_INTEGRITY

## Prioridad
MEDIUM

## Problema
Eliminar la asignación de un equipo o una ubicación a un plan no comprueba si existen órdenes de
trabajo abiertas generadas por esa asignación. El propio código lo reconoce con un `TODO`.

## Objetivo
No dejar órdenes de trabajo huérfanas de su origen ni interrumpir ciclos en curso sin advertencia.

## Comportamiento actual
`AMSYS.WebAdmin/Areas/Gestion/Controllers/PlanMantenimientoEquipo.Controller.cs` (`Eliminar` POST):
```csharp
int cantidad = await _planMantenimientoEquipoServicio.ContarAsync(new() { Id = model.Id!.Value, EmpresaId = usuario.EmpresaId });
if (cantidad == 0) ModelState.AddModelError("_", "El registro no existe.");

//TODO: VALIDAR CANTIDAD DE ORDENES DE TRABAJO PENDIENTES
```
Consecuencias verificadas:
- Las OT ya generadas conservan `PlanMantenimientoId` y `EquipoId`, pero la asignación que las
  originó desaparece. Se pierde el rastro de la posición y del contador de lanzamiento.
- Si la asignación estaba `Bloqueado`, al cerrar la OT el desbloqueo busca una fila que ya no existe
  (`GetOne(...)` devuelve `null`) y no hace nada: sin error, pero también sin efecto.
- El usuario no recibe ninguna advertencia sobre trabajo en curso.

## Comportamiento esperado
- Antes de eliminar, el sistema informa cuántas OT abiertas (`EMITIDO`) proceden de esa asignación.
- **DECISIÓN MENOR** (`D-09`): ¿bloquear la eliminación, o permitirla tras confirmación explícita?
  Recomendación técnica: permitirla con confirmación informada; bloquear dejaría al usuario sin
  salida cuando la asignación fue un error.

## Reglas de negocio involucradas
- `BR-AS-008` (eliminar sin validar) — `CONFIRMED`
- `BR-GE-008` (bloqueo FLOTANTE) — `CONFIRMED`

## Archivos potencialmente afectados

- `AMSYS.WebAdmin/Areas/Gestion/Controllers/PlanMantenimientoUbicacion.Controller.cs`
- `AMSYS.WebAdmin/Areas/Gestion/Views/PlanMantenimiento/Asignar.cshtml`

## Entidades involucradas
`PlanMantenimientoEquipo`, `PlanMantenimientoUbicacion`, `OrdenTrabajo`

## Riesgos
- **BAJO-MEDIO**: si se opta por bloquear, usuarios que hoy eliminan sin problema dejarán de poder
  hacerlo. De ahí la recomendación de confirmar en vez de bloquear.
- El conteo debe filtrar por empresa para no revelar información de otras empresas.

## Propuesta de solución
1. Antes de eliminar, contar las OT con `PlanMantenimientoId` = plan, `EquipoId`/`UbicacionId` =
   objeto y `Estado = EMITIDO`.
2. Devolver ese conteo a la interfaz para que la confirmación lo muestre:
   *"Este equipo tiene N orden(es) de trabajo abiertas de este plan. Si continúa, esas órdenes
   permanecerán pero perderán su vínculo con la programación."*
3. Implementar la opción elegida en `D-09`.
4. Si la asignación estaba bloqueada, advertirlo también.

## Tests requeridos
- Eliminar una asignación sin OT abiertas → igual que hoy.
- Eliminar una asignación con OT abiertas → aparece la advertencia con el conteo correcto.
- Las OT ya existentes no se borran ni se modifican al eliminar la asignación.
- Un usuario de otra empresa no puede eliminar la asignación ni ver el conteo.

## Criterios de aceptación
- [ ] Decisión `D-09` registrada.
- [ ] La confirmación muestra el número real de OT abiertas.
- [ ] El `TODO` del código queda resuelto o documentado como decisión.
- [ ] Ninguna OT se elimina como efecto colateral.

## Fuera de alcance
- Eliminar en cascada las OT (nunca debe hacerse).
- Reasignar OT huérfanas.
