# MNT-036

## Título
Añadir autorización a los endpoints de la API móvil de Mantenimiento

## Tipo
SECURITY

## Prioridad
HIGH

## Problema
La API que consume la aplicación móvil sólo **autentica**: valida la firma del JWT y comprueba el
token contra la base de datos. No aplica ningún control de autorización. Cualquier usuario con la
aplicación instalada puede invocar todos los endpoints, incluidos los de escritura sobre cualquier
orden de trabajo de su empresa.

## Objetivo
Que los permisos que existen en la web se apliquen también desde la aplicación móvil.

## Comportamiento actual
`AMSYS.WebAdmin/Commons/Token/FiltroToken.cs` valida el token, extrae los claims
`JWT_ID_CLAIM` y `JWT_EMPRESAID_CLAIM`, comprueba `TokenMovil` en base de datos y asigna
`HttpContext.User`. **Fin.** No consulta `Pagina`, ni `Rol`, ni `RolEstadoOrdenTrabajo`.

Endpoints de escritura sin autorización:
- `POST /api/OrdenTrabajo/guardar` — crea órdenes de trabajo
- `POST /api/OrdenTrabajo/editar`
- `POST /api/OrdenTrabajo/notificar` — cambia el estado vía `ActualizarEstadoAsync`
- `POST /api/Aviso/...`
- `POST /api/Notificacion*/...`

**Aspecto positivo verificado**: el aislamiento multi-tenant sí está correctamente resuelto. Todos
los controladores extraen `empresaId` del claim y lo aplican en los filtros. La API es, en ese
aspecto, más rigurosa que el WebAdmin.

`AMSYS.WebAPI` (proyecto separado) presenta el mismo patrón: verificar su filtro equivalente.

## Comportamiento esperado
- Los endpoints de escritura exigen que el rol del usuario tenga el permiso correspondiente.
- Las transiciones de estado se validan igual que en la web (`MNT-003`).
- Los estados permitidos por rol, si se aplican (`MNT-002`), se aplican también aquí.

## Reglas de negocio involucradas
- `BR-OT-004` (la máquina de estados no se valida) — `CONFIRMED`, también en la API
- `BR-OT-005` (estados por rol sin aplicar) — `CONFIRMED`
- `BR-AV-004` (sincronización con Aviso) — la API no la aplica, ver `MNT-007`

## Archivos potencialmente afectados
- `AMSYS.WebAdmin/Commons/Token/FiltroToken.cs`
- `AMSYS.WebAdmin/Api/Controllers/*.cs`
- `AMSYS.WebAPI/Filtros/*.cs`
- `AMSYS.WebAPI/Controllers/*.cs`

## Entidades involucradas
`Usuario`, `Rol`, `Pagina`, `RolPagina`, `OrdenTrabajo`, `Aviso`

## Riesgos
- **ALTO de regresión operativa**: los técnicos usan la aplicación móvil para su trabajo diario. Si
  su rol no tiene las páginas web correspondientes (porque nunca las necesitó), aplicar el mismo
  modelo de permisos **los dejaría sin poder trabajar**.
- El modelo de permisos actual está basado en URLs de MVC (`Area/Controlador/Accion`), que no encajan
  con las rutas de la API. Reutilizarlo tal cual es forzado.
- `FiltroToken` ya hace una consulta a base de datos por petición; añadir la carga de permisos
  aumenta la latencia de cada llamada móvil.

## Propuesta de solución
1. **Diagnóstico**: qué roles usan la aplicación móvil y qué páginas tienen asignadas hoy.
2. Plantear al propietario (`D-15`) el modelo de permisos para la API. Opciones:
   - **A**: un permiso por capacidad móvil (`movil.ordentrabajo.notificar`, …), independiente de las
     páginas web. Más limpio, exige un modelo nuevo.
   - **B**: mapear cada endpoint a una `Pagina` existente. Reutiliza el modelo, pero es artificial.
   - **C** (mínimo viable): no añadir permisos por endpoint, pero **sí** aplicar las validaciones de
     dominio que faltan: transiciones de estado (`MNT-003`) y sincronización de Aviso (`MNT-007`).
3. Implementar de inmediato la parte de la opción C, que no depende de ninguna decisión y cierra el
   riesgo funcional más concreto.
4. Implementar el modelo elegido en `D-15` como tarea separada.

## Tests requeridos
- Un técnico puede seguir notificando avance desde la aplicación (regresión principal).
- Una transición de estado inválida desde la API es rechazada.
- Cerrar una OT desde la API sincroniza el Aviso (depende de `MNT-007`).
- Ningún endpoint devuelve datos de otra empresa (ya se cumple; verificar que sigue así).

## Criterios de aceptación

- CSRF (no aplica a autenticación por Bearer).

## Dependencias

- Decisión `D-15` para el resto.

## Notas para Claude Code
- **No apliques el modelo de páginas web a la API sin el diagnóstico.** Es la vía más rápida a un
  incidente operativo: dejar a los técnicos sin poder registrar su trabajo.
- La opción C aporta seguridad real sin riesgo de bloqueo: empieza por ahí.
- Los controladores de `/Api` son la parte mejor escrita del proyecto (constructor primario, records
  de respuesta, FluentValidation). Respeta ese estilo.
