# MNT-025

## Título
Eliminar la duplicación de las validaciones `Nuevo` / `Editar`

## Tipo
CODE_QUALITY

## Prioridad
LOW

## Problema
Los métodos `Validar(XxxModel.Nuevo)` y `Validar(XxxModel.Editar)` son copias literales que sólo se
diferencian en la comprobación del `Id`. Al estar duplicados, las correcciones se aplican a una sola
copia y las reglas divergen con el tiempo.

## Objetivo
Una sola definición de las reglas de validación por entidad.

## Comportamiento actual
| Controlador | Líneas duplicadas aprox. |
|-------------|--------------------------|
| `Seccion.Controller.cs` | 45 × 2 |
| `PlanMantenimiento.Controller.cs` | 25 × 2 |
| `PlanMantenimientoEquipo.Controller.cs` | 20 × 2 (más `Validar(model, plan)` ×2) |
| `PlanMantenimientoUbicacion.Controller.cs` | similar |
| `OrdenTrabajo.Controller.cs` | tres variantes: `Nuevo`, `Editar`, `Notificar` |

Divergencias ya observadas entre copias que deberían ser idénticas:
- En `Seccion`, `Validar(Nuevo)` reporta el error de nombre bajo la clave `"Nombre"`, y
  `Validar(Editar)` bajo la clave `"Descripcion"` para el mismo campo.
- En `PlanMantenimiento`, `Validar(Nuevo)` exige `UnidadMedidaServicioId`; `Validar(Editar)` no.

## Comportamiento esperado
- Las reglas comunes viven en un solo lugar.
- Las diferencias reales entre crear y editar son explícitas y visibles.
- Los mensajes al usuario no cambian.

## Reglas de negocio involucradas
`BR-TA-003`, `BR-SE-001`, `BR-PM-009`, `BR-AS-004`, `BR-AS-005`, `BR-AS-006` — todas se conservan
**sin cambios de comportamiento**.

## Archivos potencialmente afectados
- `AMSYS.WebAdmin/Areas/Gestion/Controllers/Seccion.Controller.cs`
- `AMSYS.WebAdmin/Areas/Gestion/Controllers/PlanMantenimiento.Controller.cs`
- `AMSYS.WebAdmin/Areas/Gestion/Controllers/PlanMantenimientoEquipo.Controller.cs`
- `AMSYS.WebAdmin/Areas/Gestion/Controllers/PlanMantenimientoUbicacion.Controller.cs`
- `AMSYS.WebAdmin/Areas/Gestion/Models/*.Model.cs`

## Entidades involucradas
Ninguna se modifica.

## Riesgos
- **MEDIO**: es una refactorización sin red de tests. Un cambio de clave de `ModelState` o de texto
  puede alterar lo que ve el usuario.
- Unificar puede "corregir" involuntariamente una divergencia que alguien depende de que exista.
  Cada divergencia debe documentarse y decidirse **explícitamente**, no resolverse por omisión.

## Propuesta de solución
1. Documentar cada divergencia encontrada entre las copias, indicando cuál es la correcta.
2. Extraer una interfaz o clase base común a los pares `Nuevo`/`Editar` con los campos compartidos.
3. Un único método `Validar(IXxxValidable entidad, bool esNuevo)`.
4. Preservar **exactamente** los mensajes y las claves de `ModelState` actuales, salvo en las
   divergencias que se decida corregir (documentándolas).
5. A medio plazo, migrar a FluentValidation, como ya hace `AMSYS.WebAdmin/Api/Validations`.

## Tests requeridos
- Para cada formulario, comparar los mensajes de error antes y después: idénticos salvo en las
  divergencias corregidas a propósito.
- Guardar y editar cada entidad con datos válidos → funciona igual.
- Cada validación individual sigue disparándose.

## Criterios de aceptación
- [ ] Divergencias documentadas y decididas una por una.
- [ ] Sin duplicación de reglas comunes.
- [ ] Los mensajes al usuario no cambian de forma no intencionada.

## Fuera de alcance
- Migrar todo el módulo a FluentValidation de golpe.
- Añadir validaciones nuevas (`MNT-012`, `MNT-024`, `MNT-027`).

## Dependencias
Conviene ejecutarla **después** de las tareas que añaden validaciones (`MNT-012`, `MNT-017`,
`MNT-022`, `MNT-024`, `MNT-027`), para no refactorizar dos veces.
