# MNT-013

## Título
Introducir transacciones explícitas en los flujos multi-agregado de Mantenimiento

## Tipo
ARCHITECTURE

## Prioridad
HIGH

## Problema
No existe ni una sola transacción explícita en toda la solución (`grep BeginTransaction` → 0
resultados). La atomicidad depende por completo de que cada operación termine en un único
`SaveChangesAsync()`. En los flujos que mezclan `ExecuteUpdate` (SQL inmediato, fuera del
change-tracker) con `SaveChangesAsync` (diferido), esa garantía **no se cumple**.

## Objetivo
Que las operaciones que tocan varios agregados sean todo-o-nada.

## Comportamiento actual
Caso más grave — `PlanMantenimientoLogica.GenerarOrdenesPorEquipo`:
```csharp
if (crearOrdenes && equiposActualizar.Count > 0)
    foreach (var item in equiposActualizar)
        planMantenimientoEquipoRepositorio.Actualizar(item);   // ExecuteUpdate: SQL INMEDIATO
// ...
foreach (var item in ordenesTrabajo)
    if (crearOrdenes) { ordenTrabajoRepositorio.Save(item); ... }   // diferido
await _contexto.SaveChangesAsync();                                 // se aplica aqui
```
Si `SaveChangesAsync` falla, las posiciones de los planes **ya fueron avanzadas** por
`ExecuteUpdate`, pero las órdenes correspondientes no existen. El resultado es mantenimiento
perdido de forma silenciosa: el plan cree haber lanzado un ciclo que nunca se materializó.

Otros flujos multi-agregado sin transacción:
- `SeccionLogica.ActualizarAsync`: borra tareas/materiales/servicios y los reinserta.
- `PlanMantenimientoLogica.ActualizarAsync`: borra y reinserta `PlanMantenimientoSeccion`.
- `OrdenTrabajoLogica.NotificarAsync`: notificaciones + contadores + estado + costos.
- La sincronización Aviso ↔ OT tras `MNT-007`.

Observación adicional: `GenerarOrdenesPorEquipo` llama a `SaveChangesAsync()` **incondicionalmente**,
también en modo previsualización (`crearOrdenes = false`). Hoy es inofensivo porque el contexto está
configurado como `NoTracking`, pero es una dependencia implícita y frágil.

## Comportamiento esperado
- Los flujos multi-agregado se ejecutan dentro de `IDbContextTransaction`.
- Ante cualquier excepción se hace rollback completo.
- La previsualización no llama a `SaveChangesAsync`.

## Riesgos
- **MEDIO**: envolver en transacción cambia el comportamiento ante error, de "parcialmente aplicado"
  a "nada aplicado". Es lo correcto, pero si alguna operación **dependía** del efecto parcial
  (poco probable, pero hay que comprobarlo), cambiaría.
- Transacciones largas en la generación masiva pueden mantener bloqueos en PostgreSQL. Evaluar
  procesar por lotes si el volumen es grande.
- El contexto es *scoped* por request: no abras transacciones anidadas.

## Propuesta de solución
1. Empezar por el caso de mayor impacto: `GenerarOrdenesPorEquipo` y `GenerarOrdenesPorUbicacion`.
2. Envolver desde el primer `ExecuteUpdate` hasta después de `SaveChangesAsync`, con
   `try/catch` + `RollbackAsync` y relanzado de la excepción.
3. Hacer condicional el `SaveChangesAsync` de la previsualización (`if (crearOrdenes)`), eliminando
   la dependencia del `NoTracking`.
4. Extender el patrón a `SeccionLogica.ActualizarAsync` y `PlanMantenimientoLogica.ActualizarAsync`.
5. Documentar la convención en `legacy/ARCHITECTURE.md`.

## Tests requeridos
- Generación que falla a mitad (simular error tras el `ExecuteUpdate`) → ninguna posición avanzada
  y ninguna OT creada.
- Generación correcta de un lote de 100 órdenes → resultado idéntico al actual.
- Previsualización → cero escrituras en base de datos (verificable con log de SQL).
- Actualizar una sección con 30 tareas y provocar un fallo → las tareas originales siguen intactas.

## Criterios de aceptación

- [ ] `SeccionLogica.ActualizarAsync` es atómica.

- Verifica que ninguna capa superior abra ya una transacción antes de abrir la tuya.
