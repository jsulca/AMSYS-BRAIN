# MNT-001

## Título
Aplicar autorización `[FiltroAccion]` a todas las acciones POST del módulo de Mantenimiento

## Tipo
SECURITY

## Prioridad
CRITICAL

## Problema
Ninguna acción `[HttpPost]` del área `Gestion` lleva el atributo `[FiltroAccion]`. La autorización
por rol sólo se aplica en las acciones GET que renderizan pantallas. Cualquier usuario con sesión
válida puede invocar directamente los endpoints POST y crear, modificar o eliminar datos del módulo
de Mantenimiento, incluida la generación masiva de órdenes de trabajo.

## Objetivo
Que toda operación de escritura del módulo exija el mismo permiso de página que su pantalla
asociada, sin romper ninguna pantalla existente.

## Comportamiento actual
- `FiltroSession` (autenticación) se aplica a nivel de clase en todos los controladores.
- `FiltroAccion` (autorización) se aplica sólo a: `Index`, `Nuevo` (GET), `Editar` (GET), `Ver`,
  `Asignar`, `Notificar` (GET), `Previsualizar` (GET), `ReportePdf`.
- Sin protección: **todos** los POST, más `Listar`, `Seleccionar`, `Buscar`, `Kanban`,
  `KanbanColumna`, `KanbanConteo`, y **todas** las acciones de
  `PlanMantenimientoEquipoController` y `PlanMantenimientoUbicacionController`.

## Comportamiento esperado
- Cada POST valida el permiso de la página correspondiente.
- Cuando el POST comparte página con un GET (`Nuevo`, `Editar`), `[FiltroAccion]` sin parámetros
  ya resuelve la URL correcta porque usa `RouteData.Values["action"]`.
- Cuando el POST es una acción sin pantalla propia (`Generar`, `KanbanMover`, `Eliminar`,
  `ExportarExcel`, `PrevisualizarExcel`), usar `[FiltroAccion(Accion = "<pagina existente>")]`
  apuntando a la pantalla desde la que se invoca, **o** dar de alta la `Pagina` correspondiente.

## Riesgos
- **ALTO — riesgo de regresión**: si una `Pagina` no existe en base de datos, `FiltroAccion` devuelve
  `401` y **rompe una funcionalidad que hoy funciona**. Antes de tocar código hay que inventariar
  qué filas existen en `pagina` para el área `Gestion`.
- `FiltroAccion` lee `user.Paginas` de la **sesión**: los usuarios con sesión abierta no verán los
  permisos nuevos hasta reiniciar sesión.
- `FiltroAccion` hace `filterContext.HttpContext.Session.Get<UserInformation>(...)!` sin comprobar
  null; si se aplicara antes de `FiltroSession` lanzaría `NullReferenceException`.

## Propuesta de solución
1. **Fase de inventario (sin cambios de código)**: consultar la tabla `pagina` y listar las tuplas
   `(area, controlador, accion)` existentes para el área `Gestion`. Documentar el resultado en
   `analysis/permissions.md`.
2. **Fase de cierre incremental**, en este orden y con verificación manual entre cada paso:
   1. `PlanMantenimientoEquipo` y `PlanMantenimientoUbicacion` (hoy sin ninguna protección).
   2. POST de `HojaRuta`, `Seccion`, `PlanMantenimiento`.
   3. `OrdenTrabajo/Generar`, `OrdenTrabajo/Previsualizar` (POST), `KanbanMover`.
   4. POST de `OrdenTrabajo/Nuevo`, `Editar`, `Notificar`.
   5. Descomentar `[FiltroAccion]` en `Kanban()`.
3. Dejar sin cambios las acciones de sólo lectura que alimentan modales de otras pantallas
   (`Listar`, `Seleccionar`, `Buscar`): protegerlas rompería los modales invocados desde pantallas
   distintas. Documentar esta excepción explícitamente.

## Tests requeridos

## Notas para Claude Code
- No inventes nombres de páginas. Si una `Pagina` no existe, **detente y consulta**: crear filas en
  `pagina`/`rolpagina` es un cambio de datos que requiere autorización del propietario.
- `FiltroAccion` compara la URL en minúsculas contra `/{Area}/{Controlador}/{Accion}` con igualdad
  exacta. `[FiltroAccion(Accion = "Nuevo")]` es el mecanismo para reutilizar una página existente.
- Verifica el orden de ejecución de filtros: `FiltroSession` (clase) debe ejecutarse antes que
  `FiltroAccion` (método). Hoy funciona por el orden por defecto; si añades `Order`, no lo rompas.
