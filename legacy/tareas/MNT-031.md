# MNT-031

## Título
Extraer el JavaScript inline de las vistas grandes de Orden de Trabajo

## Tipo
MAINTAINABILITY

## Prioridad
MEDIUM

## Problema
Cuatro vistas del módulo superan las 950 líneas, con Razor y JavaScript entremezclados en un único
archivo. No se pueden probar, no se pueden reutilizar y cualquier cambio en ellas tiene un riesgo de
regresión desproporcionado.

## Objetivo
Reducir el riesgo de modificar las pantallas más críticas del módulo, sin cambiar su comportamiento.

## Comportamiento actual
| Vista | LOC |
|-------|-----|
| `OrdenTrabajo/Notificar.cshtml` | 1532 |
| `OrdenTrabajo/Ver.cshtml` | 1307 |
| `OrdenTrabajo/Editar.cshtml` | 1230 |
| `OrdenTrabajo/Nuevo.cshtml` | 952 |
| `Seccion/Editar.cshtml` | 607 |
| `Seccion/Nuevo.cshtml` | 575 |

Patrón repetido en todas: un objeto literal (`var nuevo = {...}` / `var index = {...}`) con
`ObtenerModelo`, `AbriModal`, `Set*`, seguido de un `$(function(){...})` con los manejadores.
`Seccion/Nuevo.cshtml` y `Seccion/Editar.cshtml` son casi idénticas entre sí.

Consecuencias:
- La lógica de construcción del modelo (`secciones[i].seccionId`, `tareas[i].orden`, …) se repite en
  parejas de archivos y se desincroniza.
- No hay forma de probar el JavaScript.
- Los errores de la interfaz (colspan incorrecto, `$.post` sin manejador de error) se replican al
  copiar y pegar.

## Comportamiento esperado
- El JavaScript de cada pantalla vive en un archivo propio bajo `wwwroot/js/gestion/`.
- La lógica compartida entre `Nuevo` y `Editar` de una misma entidad está en un solo lugar.
- El comportamiento visible es idéntico.

Ninguna.

## Riesgos
- **ALTO sin tests**: son las pantallas más usadas del módulo y no hay ninguna prueba automática.
- El JavaScript inline usa **valores de Razor interpolados** (`@Model.Id`, `@string.Format(...)`,
  `asp-items`). Al extraerlo hay que pasar esos valores por `data-*` en el HTML, y es fácil olvidar
  alguno.
- El *bundling* actual no está configurado: un archivo externo mal referenciado deja la pantalla
  muda, sin error visible.

## Propuesta de solución
Estrictamente incremental, **una pantalla por entrega**:
1. Empezar por la más pequeña y menos crítica: `PlanMantenimiento/Nuevo.cshtml`.
2. Mover el bloque `@section Scripts` a `wwwroot/js/gestion/plan-mantenimiento-nuevo.js`.
3. Sustituir cada interpolación de Razor por un atributo `data-*` en un elemento contenedor.
4. Verificar manualmente la pantalla completa antes de pasar a la siguiente.
5. Cuando `Nuevo` y `Editar` de una entidad estén extraídas, unificar lo común en un tercer archivo.
6. Dejar `OrdenTrabajo/Notificar.cshtml` para el final: es la más grande y la más crítica.

## Tests requeridos
Verificación manual exhaustiva por pantalla extraída:
- Cargar, rellenar y guardar con datos válidos.
- Provocar un error de validación y comprobar que se muestra igual.
- Abrir cada modal.
- Añadir y quitar filas de cada tabla dinámica.
- Comprobar en la consola del navegador que no hay errores.

## Criterios de aceptación
- [ ] Cada extracción es una entrega independiente y verificada.
- [ ] Ninguna interpolación de Razor queda perdida.
- [ ] El comportamiento de cada pantalla es idéntico al anterior.
- [ ] `Nuevo` y `Editar` de una misma entidad comparten su lógica común.

## Fuera de alcance
- Introducir un framework de frontend.
- Rediseñar las pantallas (`MNT-042`, `MNT-046`).
- Configurar bundling/minificación.

## Dependencias
Ninguna técnica, pero **es la tarea con peor relación riesgo/beneficio del backlog sin tests**.
Ejecutarla después de las tareas de seguridad e integridad.

## Notas para Claude Code
- **No extraigas varias pantallas en el mismo commit.** Una por commit, verificada, o será imposible
  localizar qué rompió qué.
- Presta especial atención a `@string.Format("{0}(items)", callBack)` en los modales `_Seleccionar`:
  Razor genera el nombre de la función de callback dinámicamente. Ese patrón **no se puede extraer
  tal cual**; hay que pasar el nombre por `data-callback` y resolverlo en tiempo de ejecución.
- Si dudas de una pantalla, no la extraigas. El código feo que funciona es mejor que el código limpio
  que rompe la operación.
