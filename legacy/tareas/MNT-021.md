# MNT-021

## Título
Cerrar el IDOR de lectura en `HojaRuta/Editar`

## Tipo
SECURITY

## Prioridad
HIGH

## Problema
La acción que abre el modal de edición de una Hoja de Ruta no filtra por empresa. Cualquier usuario
autenticado puede leer el código y la descripción de las hojas de ruta de cualquier otra empresa
iterando identificadores.

## Objetivo
Que ninguna lectura del módulo devuelva datos de otra empresa.

## Comportamiento actual
`AMSYS.Logicas/Gestion/HojaRuta.Logica.cs`:
```csharp
public async Task<HojaRuta?> BuscarPorIdAsync(int id, bool conDetalles = false)
{
    HojaRuta? _ = await _repositorio.GetOneAsync(x => x!.Id == id);   // sin EmpresaId
    ...
}
```
- `HojaRutaController.Editar(int id, string callBack)` la invoca **sin** pasar `EmpresaId` — de hecho
  la acción ni siquiera recibe `UserInformation`.
- `HojaRutaController.Ver` sí comprueba `_.EmpresaId != usuario.EmpresaId`, lo que demuestra que la
  omisión en `Editar` es un descuido, no una decisión.
- El POST `Editar` sí filtra (`GetOne(x => x.Id == ... && x.EmpresaId == ...)`), por lo que **no hay
  escritura cruzada**: el impacto es de confidencialidad, no de integridad.

Además, `conDetalles = true` carga secciones, tareas, materiales y servicios: si alguna ruta llamara
a este método con detalles y sin filtro, la fuga sería mucho mayor.

## Comportamiento esperado
- `BuscarPorIdAsync` recibe y aplica `EmpresaId` obligatoriamente.
- Un identificador de otra empresa devuelve "no encontrado", sin distinguirlo de un id inexistente.

## Reglas de negocio involucradas
Ninguna regla de dominio cambia. Ver `legacy/analisis/permissions.md` SEC-03.

## Archivos potencialmente afectados
- `AMSYS.Logicas/Gestion/HojaRuta.Logica.cs`
- `AMSYS.Servicios/Gestion/IHojaRuta.Servicio.cs`
- `AMSYS.WebAdmin/Areas/Gestion/Controllers/HojaRuta.Controller.cs`
- Cualquier otro llamador de `IHojaRutaServicio.BuscarPorIdAsync` (buscar antes de cambiar la firma)

## Entidades involucradas
`HojaRuta`, `Seccion`, `Tarea`

## Riesgos
- **BAJO**: cambiar la firma del servicio obliga a actualizar todos los llamadores. Hay que
  localizarlos todos antes (búsqueda global de `BuscarPorIdAsync` sobre `IHojaRutaServicio`).
- Si alguna llamada legítima no dispone de `EmpresaId`, hay que revisarla caso por caso.

## Propuesta de solución
1. Localizar todos los llamadores de `IHojaRutaServicio.BuscarPorIdAsync`.
2. Cambiar la firma a `BuscarPorIdAsync(HojaRutaFiltro filtro, bool conDetalles = false)`,
   alineándola con el patrón que ya usan `Seccion` y `PlanMantenimiento`.
3. Aplicar `EmpresaId` en el `GetOneAsync` y también en la carga de secciones.
4. Actualizar `HojaRutaController.Editar` para recibir `UserInformation` y pasar el filtro.
5. Revisar `Ver` para que use el mismo mecanismo y deje de comparar a posteriori.
6. **Auditar el resto del módulo** en busca del mismo patrón: cualquier `GetOne`/`GetOneAsync` por
   `Id` sin `EmpresaId`.

## Tests requeridos
- Usuario de la empresa A abre `Editar` de una hoja de ruta de A → funciona.
- Usuario de A abre `Editar` de una hoja de ruta de B → "no encontrado", sin datos filtrados.
- `Ver` mantiene su comportamiento actual.
- El POST `Editar` sigue funcionando.

## Criterios de aceptación
- [ ] `BuscarPorIdAsync` no puede invocarse sin `EmpresaId`.
- [ ] `Editar` de otra empresa devuelve "no encontrado".
- [ ] Auditoría del patrón en el resto del módulo documentada en `legacy/analisis/permissions.md`.

## Fuera de alcance
- IDOR de las asignaciones de plan (`MNT-028`), que sí permite escritura cruzada y es más grave.
- Validación de FKs de otra empresa (`MNT-022`).

## Dependencias
Ninguna. Conviene ejecutarla junto a `MNT-028`, que es el mismo tipo de defecto.

## Notas para Claude Code
- Cambiar la firma a un objeto filtro es preferible a añadir un parámetro `int empresaId`: alinea
  esta lógica con el patrón dominante del módulo y hace más difícil olvidarlo en el futuro.
- Devuelve siempre el mismo mensaje para "no existe" y "no es tuyo": distinguirlos permite enumerar
  identificadores.
