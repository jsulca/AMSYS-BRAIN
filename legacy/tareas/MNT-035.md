# MNT-035

## Título
Añadir protección CSRF a los formularios del módulo

## Tipo
SECURITY

## Prioridad
MEDIUM

## Problema
Ningún POST del módulo valida un token anti-falsificación. Las peticiones se envían como
`application/x-www-form-urlencoded`, formato que un sitio de terceros puede emitir desde el navegador
de la víctima con su cookie de sesión.

## Objetivo
Que ninguna acción de escritura pueda dispararse desde un origen ajeno.

## Comportamiento actual
- No hay `[ValidateAntiForgeryToken]` ni `[AutoValidateAntiforgeryToken]` en el módulo.
- Las vistas no emiten `@Html.AntiForgeryToken()`.
- Todas las peticiones se hacen con `$.ajax` / `$.post` en formato de formulario.
- La sesión se valida contra `TokenWeb` en base de datos, lo que protege frente al robo de sesión,
  **pero no frente a CSRF**: la cookie viaja igual en una petición cross-site.
- Acciones especialmente sensibles: `POST /Gestion/OrdenTrabajo/Generar` (crea órdenes reales),
  `POST /Gestion/PlanMantenimientoEquipo/Eliminar`, `POST /Gestion/OrdenTrabajo/KanbanMover`.

Nota: la API (`/Api` y `AMSYS.WebAPI`) usa `Authorization: Bearer`, que **no** es vulnerable a CSRF.
El problema es exclusivo del WebAdmin.

## Comportamiento esperado
- Cada POST del módulo exige un token válido.
- Las peticiones AJAX lo envían automáticamente.
- Un POST sin token devuelve `400`.

## Reglas de negocio involucradas
Ninguna. Ver `analysis/permissions.md` SEC-07.

## Archivos potencialmente afectados
- `AMSYS.WebAdmin/Program.cs` (configuración de antiforgery)
- `AMSYS.WebAdmin/Views/Shared/_Layout.cshtml` (emisión del token)
- `AMSYS.WebAdmin/wwwroot/js/**` (configuración global de `$.ajaxSetup`)
- Todos los controladores del área `Gestion`

## Entidades involucradas
Ninguna.

## Riesgos
- **ALTO de regresión**: si un solo formulario deja de enviar el token, esa pantalla se rompe. El
  módulo tiene decenas de puntos de envío, muchos construidos a mano dentro de las vistas.
- `[AutoValidateAntiforgeryToken]` global afectaría también a `Areas/Api`, cuyo `FiltroToken` no lo
  necesita: hay que **excluir explícitamente** los controladores de API con `[IgnoreAntiforgeryToken]`.
- Las descargas por formulario dinámico (`PrevisualizarExcel` crea un `<form>` por JavaScript)
  necesitan el token añadido a mano.

## Propuesta de solución
1. Emitir el token una vez en `_Layout.cshtml`.
2. Configurar `$.ajaxSetup` para añadir la cabecera `RequestVerificationToken` en todas las
   peticiones no-GET, y registrar el nombre de esa cabecera en el servicio de antiforgery.
3. Aplicar `[ValidateAntiForgeryToken]` **controlador por controlador**, verificando cada pantalla,
   en este orden:
   1. `PlanMantenimientoEquipo`, `PlanMantenimientoUbicacion` (pocos formularios)
   2. `HojaRuta`, `Seccion`
   3. `PlanMantenimiento`
   4. `OrdenTrabajo` (el más grande, al final)
4. Excluir explícitamente los controladores de `Api`.
5. Tratar aparte los formularios de descarga creados por JavaScript.

## Tests requeridos
Por cada controlador protegido:
- Todos sus formularios y acciones AJAX siguen funcionando.
- Un POST sin token devuelve `400`.
- Las descargas de Excel siguen funcionando.
- La API móvil no se ve afectada.

## Criterios de aceptación
- [ ] Cada controlador se protege en una entrega verificada por separado.
- [ ] Ningún formulario del módulo deja de funcionar.
- [ ] Los controladores de API quedan excluidos.
- [ ] Un POST sin token es rechazado.

## Fuera de alcance
- Otros módulos (`Administracion`, `Logistica`, `Seguridad`).
- Cabeceras de seguridad adicionales (CSP, HSTS).

## Dependencias
Conviene ejecutarla **después** de `MNT-001` y `MNT-028`: la autorización y el aislamiento por
empresa cierran vectores de mayor impacto.

## Notas para Claude Code
- **No apliques `[AutoValidateAntiforgeryToken]` globalmente de una vez.** Romperías el módulo entero
  a la vez y sin forma sencilla de saber qué pantalla falló.
- El módulo tiene muchos formularios dinámicos y modales cargados por AJAX. Cada uno es un punto
  potencial de fallo: verifica pantalla por pantalla.
